# 项目经验生命周期

这是仓库级工程经验，不写入或修改 Codex 全局 memories，也不保存用户对话、密钥或业务数据。普通小改动不必创建经验。

候选写作 `.agents/lessons/YYYY-MM-DD-topic.md`，用 [模板](../../docs/quality/templates/lesson.md)。一条经验只描述一个有证据的原因和适用范围。

状态：candidate → validated → adopted；不成立为 rejected，被新事实取代为 superseded。candidate/validated 只是参考，不能变成强制指令。

- candidate：复现记录、修复证据和适用条件齐全；区分观察与假设。
- validated：独立场景或回归验证支持，写明不能适用的反例；一次样例不能推出普遍规则。
- adopted：用户明确接受对应规则变更，记录决定来源和版本，然后更新唯一所属 Skill/规范并链接本记录。不靠 Agent 自评晋升。
- rejected/superseded：记录原因及替代项，不在后续任务中继续作为现行约束。

用户对具体行为的明确纠正可直接更新该行为约定，但不能泛化成额外产品规则。对审查/权限/验收门槛的改变必须单列展示，不能藏在“学习优化”里。

同类问题先查已有记录，补证据而非复制规则。每次相关复发检查：旧经验是否被找到、范围是否正确、测试是否漏掉真实入口。撤回无效规则时保留原因；没有证据就不宣称“持续学习已改善”。

后续若产品内实现经验库，其候选、证据、复核状态、版本、适用范围与 embedding 应存 SQLite，检索结果是参考材料，不自动成为系统指令。跨工作空间隔离、敏感信息处理与用户删除必须覆盖原文和向量。
