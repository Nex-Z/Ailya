# SQLite 与向量存储架构

状态：正式版强制约束与实施设计；首阶段已接入 Core / SQLite 及向量底座，备份恢复界面及一致性校验已接入，见 [备份恢复与启动](implementation/backup-runtime.md)；自动保留策略和发布产物验收仍待实现。首阶段见 [阶段记录](implementation/phase-1.md)。

## 存储边界

SQLite 是 Core 的业务事实来源。会话、消息、任务及事件、问题/回答/截止时间、子 Agent 关系、Agent/Group、厂商模型配置、扩展配置、定时任务与运行记录、IM 账号配置、权限规则、Token 用量、附件元数据、差异记录、记忆片段及向量均须持久化。

浏览器 localStorage 仅可保存非关键展示偏好，不能成为另一套业务主库。浏览器 File 是未提交草稿；正式提交后由 Core 接收并持久化。用户原项目文件仍位于 Workspace，不搬进数据库；大附件原始字节可存 Core 管理的文件目录，SQLite 保存稳定 ID、路径、校验值、大小、归属和生命周期，备份时一并处理。

凭据在 SQLite 中只保存加密值或操作系统凭据引用，解密密钥不与数据库一起存放，也不返回前端。此设计不代表当前数据库自动加密。

## 连接与迁移

由 Core 独占数据库访问入口；前端使用 API/事件。计划使用 bun:sqlite + Drizzle，向量扩展专用 SQL 可通过封装的参数化 repository 执行。不为向量另起常驻数据库服务。

数据目录可配置，独立于源码、dist 和安装目录；数据库路径由 Core 解析为绝对路径。启用外键约束；WAL、busy timeout 和写事务策略需在真实运行环境验证。事务短小，模型/网络请求放在事务外。

迁移文件版本化，记录 schema 版本；首次安装与旧版升级均测试。升级前备份，失败不丢数据。在线备份使用 SQLite 一致性备份机制，不能只复制活跃主文件而遗漏 WAL；恢复验证关系、附件、向量数量和查询结果。

## 向量实现

SQLite 必须具备实际向量相似度检索，而不只是保存 embedding JSON。

优先验证 sqlite-vec：官方提供 Bun 安装入口，Bun 提供 loadExtension API。依赖版本在接入时固定，实测 Windows x64、目标发布平台和打包后的扩展加载；候选不等于已验收。不兼容时记录证据并选择其他 SQLite 内向量方案，不擅自切换外部数据库或假装向量搜索可用。

每个向量记录需关联原文片段、来源实体/会话/工作空间、内容哈希、embedding 厂商与模型标识、模型版本或修订、维度、距离度量、索引版本和更新时间。聊天模型和 embedding 模型独立配置，不假定聊天厂商提供 embedding。

不同模型/维度不得混入同一搜索空间；切换模型采用新索引和可恢复重建流程，完成后切换，保留原文。新增、修改、删除和权限变化必须同步向量生命周期；过期向量不能被召回。

搜索先限定授权的会话/工作空间与索引版本，再返回 Top-K；隔离过滤必须在有效候选集合上生效，不以全库 Top-K 后过滤替代范围检索。参数化查询、可中断批处理和幂等索引任务。失败时暴露真实状态，文本搜索若作为降级必须明确区分。

## 必须通过的验收

1. 建库、迁移、重启后普通数据和向量仍可查询。
2. 固定向量样本的最近邻顺序、范围隔离和维度错误处理正确；另用真实 embedding 服务验证完整链路。
3. 原文更新/删除、索引重建、任务中断恢复后无陈旧召回。
4. 导入原型 localStorage 数据时预览和去重，保留原数据；不把演示会话自动当成生产记录。
5. 一致性备份恢复后业务数据、附件关联、向量结果一致。
6. 发布产物在目标机能加载向量扩展，不依赖开发机 node_modules 或绝对路径。
